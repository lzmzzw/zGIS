# 大数据使用与验证

当前采用完整内存工作副本，适合有界的大文件和大表子集；尚未实现磁盘分块存储、按视口取数或任意规模全表编辑。文件大小、记录数量与几何复杂度分别影响实际内存和耗时。

## 当前容量

| 路径 | 上限与行为 |
| --- | --- |
| 桌面导入、GeoJSON/CSV 保存、恢复副本 | 单文件及单批导入合计最多 256 MiB；规范化后的保存/恢复内容独立检查大小 |
| Web 导入 | 单批最多 100 MiB，文件顺序读取，本地处理 |
| Worker 结果传输 | 普通批次最多 2 MiB 且 1024 个要素；大单要素独批，单要素及图层元数据各最多 64 MiB |
| ZIP 导入 | 最多 2000 个成员、合计 200 MiB 解压内容；SHP 保存/导出另有格式与成员预算 |
| SHP 导出 | 共享内核的组件合计和 ZIP 各最多 100 MiB；不能由桌面读入上限推断导出容量 |
| MySQL / PostGIS 图层 | 最多 100000 条、100 MiB 完整结果，包含主键和提交基线；可选地图范围缩小读取 |
| GDB 只读图层 | 默认 10000、最多 100000 要素及 100 MiB 结果；目录/ZIP、字段与坐标独立预算见 [GDB 说明](gdb.md#容量与一致性) |
| 数据库提交 | 最多 10000 条；MySQL 另限 16 MiB，单属性 64 KiB、单几何 1 MiB 的读取保护保留 |
| 空间分析 | 每输入层及结果最多 100000 要素；另限 100 万顶点、100 MiB 输入/结果、100 万候选对、累计 1000 万工作顶点和执行时限 |
| MCP 外部文件读取 | 继续保持 100 MiB，工作区快照与响应另有独立预算，见 [空间分析接入](spatial-mcp.md) |
| 显示与属性 | 属性表每页 100 条；大图层分批建图与搜索。字段概览仍限制 10000 要素，标注每层最多 1000 条 |

数据库达到条数上限会明确标记当前不是全表；超过字节预算整体拒绝。分析超预算报错，不返回截断结果。读取大表时先设置合理条数和地图范围，确保当前子集适合下一步分析。编辑超过单次提交条数的数据前，应分批载入和修改。

## 实现与测量

文件通过元数据和二进制 IPC 进入 Worker，GeoJSON 单次无损解析，CSV 预览只取完整前缀。解析结果分批回传，主线程确认后，Worker 释放该批源要素再继续。GeoJSON/CSV 保存与恢复备份按要素/行生成文本，不缓存完整图层 JSON，也不先拼接完整正文；每片最多 1 MiB，原生逐片写入临时文件，以 64 KiB 缓冲完成校验与原子发布。失败保留原文件，未完成传输五分钟后释放。地图和搜索在片间交还事件循环，取消或更新后的旧作业不发布过期结果；数据库按行累计结果预算，目标表验证不重复扫描全库元数据。具体实现和可复现基准见 [前端性能](frontend-performance.md) 与 [空间计算性能](spatial-performance.md)。

`pnpm test` 覆盖真实 100 MiB 以上有效输入、10 万 XYZ 点完整性、Worker 超时/取消/并发、二进制文件契约和显示作业取消；`tests/large-data.spec.ts` 覆盖 10 万点导入、末条搜索、地图同步与分页编辑焦点。数据库容量浏览器测试使用 adapter mock；Rust 校验 SQL、预算和完整基线，均不等于真实数据库吞吐验收。

```powershell
pnpm test
pnpm build
pnpm exec playwright test tests/large-data.spec.ts tests/database-capacity.spec.ts
pnpm build:web
pnpm test:web
. ./scripts/msvc-environment.ps1
cargo test --manifest-path src-tauri/Cargo.toml --lib --locked
cargo test --manifest-path crates/spatial-core/Cargo.toml --locked
```

浏览器桌面测试需要另开 `pnpm dev`。原生验证使用独立应用标识和专用 WebView 数据目录，不覆盖已安装程序或用户工作区；脚本会先核对测试应用身份。

### Windows 原生实测

2026-11-03，本机隔离 Debug 应用通过真实文件菜单导入 118451012 字节（约 113 MiB）的 GeoJSON，包含 50000 个点，每条有 2200 字节长属性。未启用跳过恢复日志或备份 IPC 的诊断开关。

| 操作 | 分批内存优化前 | 分批内存优化后 |
| --- | --- | --- |
| 打开文件菜单至完成导入、地图同步（含文件对话框） | 8.36 秒 | 11.04 秒 |
| 搜索末条记录 | 3.22 秒 | 4.77 秒 |
| 验收脚本读取并确认原生恢复副本已完整写入 | 7.11 秒 | 15.20 秒 |
| WebView 重载、恢复图层并再次找到末条 | 5.61 秒 | 4.89 秒 |
| 编辑末条属性、覆盖保存并逐条核验输出 | 19.03 秒 | 19.61 秒 |
| 进程树 private memory 采样峰值 | 6.46 GiB（38 个样本） | 4.00 GiB（47 个样本） |

两次使用相同输入指纹和同一验收脚本，均完成全部 50000 条记录的顺序、名称、长属性和坐标核验，未观测到页面异常或渲染进程崩溃。原报告为 `output/performance-20261103/native-large-files/2026-11-03T09-37-20-205Z/report.json`；分批版本报告为 `output/memory-batching-20261103/native/2026-11-03T10-32-48-859Z/report.json`，均绑定可执行文件、脚本和保存结果 SHA-256。新版本 GeoJSON 按紧凑格式逐要素写出，换行和缩进变化，数据语义保持一致。

分批版本的应用进程树 private memory 采样峰值由 6936059904 降至 4300197888 字节，约 **6.46 → 4.00 GiB，降低 38%**。内存成本仍然较高。两次均为本机隔离 Debug + CDP 单次运行；采样值不等于严格峰值，也不代表单独的 JavaScript 堆。分批传输、额外字节计量和临时文件读写有耗时成本，本次导入/搜索及恢复副本确认更慢，重载更快，保存耗时接近；不能据此推定稳定的端到端提速比例，也不构成任意复杂几何或任意 256 MiB 文件的流畅性保证。

## 实际限制

字节预算约束序列化数据，不能作为全进程内存上限。工作副本、地图投影、撤销引用和解析缓冲区会同时占用内存。文件解析内部、恢复读取/JSON 解析仍是全量处理，数据库提交基线的规范化也保留完整副本；单个要素序列化仍可能产生大字符串。临时盘和目标盘需要暂存空间，强杀可能留下发布阶段的同目录临时文件；正式文件仍受原子替换保护。复杂面运算只支持协作式取消，单次底层几何调用结束前不能强制中断。

本轮未验证真实 PostGIS/MySQL 的网络、TLS、服务端执行计划和超大单行，也未做 macOS 实机测试或安装升级验收。GB 级文件和百万级数据库图层仍需后续磁盘存储、按视口加载与服务端分页方案；不能仅继续提高当前内存上限。
